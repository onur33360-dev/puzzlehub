# SlySwipe — Official GAME_POOL Roadmap

> **Version:** 1.0 — July 2026  
> **Purpose:** Product roadmap, not a brainstorm. Every game below has a proven track record of player engagement in the real world.  
> **Methodology:** Market analysis of Voodoo, Ketchapp, SayGames, Kwalee, YouTube Playables (75+ titles), Poki top charts, CrazyGames top charts, Google Play Instant, and App Store download leaders from 2012–2025. Weighted by downloads, retention, and session metrics where available.

---

## Strategic Vision

SlySwipe's goal is **30–40% puzzle, 60–70% other casual genres**.  
The platform succeeds if a user can open it with 2 minutes of free time and feel rewarded. Every game must pass this test:

> *"Can someone understand and enjoy this in under 10 seconds?"*

---

## Scoring Legend

| Metric | Description |
|---|---|
| **Replay** | How often players naturally restart (1–10) |
| **Retention** | Day-7 / Day-30 retention potential (1–10) |
| **Viral** | Shareability / screenshot / challenge potential (1–10) |
| **Monetize** | Ad + IAP potential (1–10) |
| **SlySwipe Fit** | How naturally it fits into the platform (1–10) |
| **Difficulty** | Dev effort: Easy / Medium / Hard |
| **Session** | Average single play duration |

## KEY STRATEGIC INSIGHTS

### 1. The Hybrid-Casual Opportunity
<cite index="9-1">Hybrid-casual games aim to retain players for 60–90 days, far above typical hyper-casual levels, by layering light meta-progression on top of simple core mechanics.</cite> Every game in this pool should be designed with at least one hybrid layer: a streak system, daily challenge, personal best board, or cosmetic unlock.

### 2. The Daily Challenge Lock-In
Games with a daily challenge format (Wordle, Sudoku, Spelling Bee, Nonogram, Connections) have the highest Day-30 retention on the platform regardless of fun score. Prioritize building the daily challenge infrastructure in Phase 1 so it's ready when the puzzle-heavy games arrive.

### 3. Session Length Balance
A healthy platform needs:
- **Under 1 min sessions** (Reaction Test, Timing Dash, Don't Touch Spikes) → Impulse openers
- **1–5 min sessions** (Helix Jump, Block Blast, Lane Runner) → Core engagement
- **5–15 min sessions** (Sudoku, Solitaire, Tower Defense) → Deep engagement & monetization

### 4. The "First 10 Seconds" Test
<cite index="17-1">When a user is scrolling through their feed, their attention span is measured in fractions of a second. If your game takes too long to load or requires explanation, they will scroll away.</cite> Every Phase 1 and 2 game must be playable within 5 taps of launching the app.

### 5. Merge Games Are Underrated
<cite index="3-1">The revenue chart reveals that puzzle/merge hybrid titles consistently outperform pure arcade titles in IAP monetization.</cite> Merge games should be a priority despite lower viral scores — they monetize better than they acquire.

### 6. One-Handed Design Is Non-Negotiable
Every game in Phase 1 and Phase 2 must work with one thumb, held vertically. This enables play in transit, in queues, and with a hand occupied — which is when mobile gaming happens.

## ENGINEERING NOTES (Appended)

> **Scope of this section:** implementation guidance only, specific to SlySwipe's current stack. It does not alter, override, or second-guess any ranking, score, or roadmap decision above — those remain the product/market source of truth. This section exists to flag *how* things get built here, not *what* or *in what order* gets built.

> **Current stack constraints** (see root `CLAUDE.md`): vanilla JavaScript, HTML, CSS — no build step, no bundler, no framework, no package manager. ### Stack-risk flags by roadmap category

These flag *implementation risk in this codebase specifically* — the roadmap's Easy/Medium/Hard labels reflect general market/dev effort, not a vanilla-JS-no-dependency constraint.

- **3D-presentation arcade titles** — Helix Jump, Crossy Road, Hole.io Clone — are conventionally built with a 3D engine. A convincing result in flat DOM/CSS or 2D Canvas is a materially bigger art+engineering lift than their "Easy" label suggests in this stack. Consider either an explicit 2D-honest reinterpretation of the mechanic, or flag as higher effort than labeled.
- **Physics-dependent titles** — Cut the Rope, Angry Birds Lite, Plinko Drop, Wrecking Ball, Tower Balance, Sand Fall, Merge Fruits (Suika) — need at least a lightweight physics simulation (gravity, collision, restitution). None of these can be built to a satisfying feel with pure CSS transitions. Bringing in a physics library (e.g. Matter.js) or hand-rolling a minimal 2D physics step is a real dependency/architecture decision per `CLAUDE.md`'s "no new dependencies without an explicit decision" rule — needs sign-off before any of these are scheduled, not discovered mid-build.
- **Daily-challenge-format titles** — Wordle, Sudoku (daily), Spelling Bee, Nonogram, Connections — require deterministic per-day puzzle generation (e.g. date-seeded PRNG) and streak-aware state, distinct from every other game's per-session randomness. This can be done client-side without a backend (consistent with the current mocked/no-backend stage), but it's a shared subsystem worth building once, not per-game — natural candidate for the "build when first needed" moment the product owner has already indicated preference for (build games first, extract shared systems once patterns repeat).
- **Card/board and idle/incremental titles** (Solitaire, FreeCell, Blackjack, Dominoes, Cookie Clicker, Idle Bakery, Idle Miner, Idle Garden) are the best stack fit in the entire pool — no physics, no 3D, pure state/timers/DOM rendering, directly compatible with the existing architecture and `localStorage`-backed state model.

### On genre-mix math vs. the 30–40% puzzle target

The Phase 1+2+3 tables above total **21% puzzle** (16 of ~77 scheduled titles) against the stated 30–40% target. Read in isolation this looks like a shortfall — but SlySwipe already ships 7 puzzle games outside this roadmap's count. Net of the existing catalog, a lighter puzzle build-rate in new phases may already be correct rather than a gap. Recommend deciding explicitly whether the 30–40% target is meant to apply to the *total* catalog (existing + roadmap) or to *new builds* going forward, since the phase tables currently read as if built from zero.
